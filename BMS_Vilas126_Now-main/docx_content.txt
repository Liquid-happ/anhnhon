Cấu trúc tổ chức lại mã nguồn firmware BMS_Vilas126

1. Mục tiêu tổ chức lại mã nguồn
Firmware BMS_Vilas126 ban đầu có nhiều logic tập trung trong các file lớn, đặc biệt là main.c và các file giao tiếp như bq_bms_pylon.c, bq_bms_485.c, file header BQ76952 cũ. Cách tổ chức này giúp triển khai nhanh ở giai đoạn thử nghiệm, nhưng gây khó khăn khi mở rộng, kiểm thử, bảo trì và thương mại hóa sản phẩm.
Việc tổ chức lại mã nguồn được thực hiện theo hướng phân lớp chức năng, tách biệt rõ:
Lớp khởi tạo phần cứng do CubeMX sinh ra.
Lớp ứng dụng điều phối vòng đời firmware.
Lớp dịch vụ nghiệp vụ BMS.
Lớp giao thức truyền thông.
Lớp driver phần cứng.
Lớp dùng chung.
Lớp cấu hình hệ thống.
Lớp tài liệu kỹ thuật.
Mục tiêu chính là giữ lại logic cũ, nhưng phân rã lại thành các module có trách nhiệm rõ ràng, dễ kiểm thử, dễ thay thế và dễ mở rộng.

3. Nguyên tắc phân lớp kiến trúc
Firmware được tổ chức lại theo 7 lớp chính.
Lớp
Thư mục
Vai trò chính
Hardware generated layer
Core/, Drivers/
Chứa mã do STM32CubeMX sinh ra, cấu hình clock, GPIO, I2C, UART, CAN, interrupt, HAL
Application layer
App/
Điều phối vòng đời firmware, scheduler, state machine tổng thể
Service layer
Svc/
Chứa các nghiệp vụ BMS: đo lường, bảo vệ, fault, điều khiển, SOC, SOH, cân bằng cell, lưu trữ, giao tiếp pack, inverter, HMI
Protocol layer
Proto/
Đóng gói dữ liệu theo giao thức Pylon CAN, Pylon RS485, DWIN HMI
Driver layer
Drv/
Làm việc trực tiếp với phần cứng: BQ76952, W25Qxx, DS1307, CAN, UART, RS485, LED, buzzer
Common layer
Common/
Kiểu dữ liệu chung, context hệ thống, mã lỗi, tick, filter, Kalman, NTC, ring buffer
Configuration layer
Cfg/
Tập trung toàn bộ tham số cấu hình hệ thống, bảo vệ, giao tiếp, phần cứng, feature flag
Nguyên tắc quan trọng:
Core không chứa logic BMS.App không truy cập trực tiếp phần cứng.Svc không gọi HAL trực tiếp.Proto chỉ đóng gói giao thức, không điều khiển phần cứng.Drv là lớp duy nhất được phép gọi HAL trực tiếp.Common không phụ thuộc vào nghiệp vụ cụ thể.Cfg chứa tham số, không chứa logic xử lý.

4. Mô tả chi tiết từng phần
4.1. Thư mục Core/
Vai trò
Core/ là khu vực do STM32CubeMX sinh ra, giữ nguyên vai trò khởi tạo nền tảng vi điều khiển STM32F103VET6. Sau khi refactor, Core/ không chứa logic nghiệp vụ BMS mà chỉ thực hiện:
Khởi tạo HAL.
Cấu hình clock.
Khởi tạo GPIO, I2C, UART, CAN, SPI, IWDG, timer nếu có.
Xử lý interrupt.
Gọi tầng ứng dụng thông qua App_Init() và App_Run().
Phân bổ file
File
Chức năng sau refactor
Nguồn tách từ code cũ
Core/Src/main.c
Điểm vào chương trình. Chỉ gọi HAL_Init(), SystemClock_Config(), MX_xxx_Init(), sau đó gọi App_Init() và App_Run() trong vòng while(1)
Từ main.c cũ, giữ phần khởi tạo MCU, tách toàn bộ logic BMS ra ngoài
Core/Inc/main.h
Khai báo GPIO, handle ngoại vi, macro phần cứng do CubeMX sinh ra
Giữ từ CubeMX
stm32f1xx_it.c/.h
Xử lý ngắt hệ thống, ngắt ngoại vi
Giữ từ CubeMX
stm32f1xx_hal_msp.c
Cấu hình MSP cho HAL peripheral
Giữ từ CubeMX
system_stm32f1xx.c
Cấu hình hệ thống lõi Cortex-M3
Giữ từ CubeMX
Nguyên tắc sau refactor
main.c không còn chứa các đoạn xử lý như đọc cell, tính SOC, gửi CAN, xử lý fault, bật/tắt MOS. Toàn bộ phần này được chuyển xuống App/, Svc/, Proto/, Drv/.

4.2. Thư mục App/
App/ là lớp điều phối cấp cao của firmware. Đây là nơi quản lý vòng đời hệ thống, scheduler và state machine.

Khởi tạo context toàn hệ thống.
Khởi tạo các service chính của BMS.
Khởi tạo các service phụ như CAN, RS485, HMI, Store, Indicator.
Khởi tạo scheduler.
Chạy vòng lặp ứng dụng thông qua App_Run().

Hàm

Gom toàn bộ trình tự khởi tạo firmware BMS
Tách từ phần khởi tạo trong main.c cũ
App_Run()

Tách từ vòng while(1) trong main.c cũ
Ý nghĩa refactor

main.c -> chỉ chạy nền MCUapp.c  -> điều phối ứng dụng BMS

13. Ý nghĩa kỹ thuật của việc tổ chức lại
Sau khi tổ chức lại, firmware đạt các lợi ích:
Dễ hiểu hơn: mỗi file có một trách nhiệm rõ ràng.
Dễ debug hơn: lỗi đo lường, lỗi protection, lỗi CAN, lỗi HMI được tách riêng.
Dễ kiểm thử hơn: có thể bật/tắt từng feature bằng feat_cfg.h.
An toàn hơn: FET, CAN, RS485, flash, buzzer không tự động tác động phần cứng nếu chưa bật feature.
Dễ mở rộng hơn: thêm inverter protocol, thêm HMI page, thêm storage version không ảnh hưởng lõi BMS.
Dễ thương mại hóa hơn: kiến trúc có phân lớp rõ, phù hợp bảo trì dài hạn.
Dễ truy vết logic cũ: mỗi module đều có mapping từ function cũ sang function mới.

15. Kết luận
Cấu trúc mới của firmware BMS_Vilas126 đã chuyển từ mô hình tập trung trong main.c và một số file giao tiếp lớn sang mô hình phân lớp rõ ràng:
Core  -> nền MCUApp   -> điều phối ứng dụngSvc   -> nghiệp vụ BMSProto -> giao thức truyền thôngDrv   -> driver phần cứngCommon -> dùng chungCfg   -> cấu hìnhDoc   -> tài liệu kỹ thuật
Cách tổ chức này giúp firmware dễ đọc, dễ kiểm thử, dễ kiểm soát an toàn và phù hợp hơn với yêu cầu phát triển sản phẩm BMS thương mại dùng BQ76952, STM32F103VET6, CAN inverter, RS485 parallel pack, DWIN HMI, W25Qxx flash và DS1307 RTC.
